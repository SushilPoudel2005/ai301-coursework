# Rubric: is this reproduction package ready to post?

Every check reads the thing itself against the issue, never the shape of the write-up. In live mode on a claim-only draft, only the two Comms checks apply; the rest report `unclear` ("not yet applicable") and are left out of the verdict.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment recorded | The repro report's environment record, read against the version/OS/runtime the issue targets and the facts the repo's bug template asks for (repo-facts "bug reports" line) | The report names the exact version of the software under test plus the OS and runtime (and install method where the template asks for it), enough for a stranger to rebuild the environment, AND those match what the issue targets or any difference is called out in the report. Full diagnostic dumps the template mentions (such as a package list) are not required when the named versions already pin the environment. A bare "latest" or "my machine" fails. | required |
| Steps followable | The repro report's commands/actions, from starting state to trigger | A stranger could run them in order: every command or action is written out (not described), and the input that triggers the behavior is shown, quoted verbatim from the issue (the report says which), or referenced from inputs the issue states exactly when the report names the parameters it used (ranges, options, parser, file contents), or described precisely enough that the trigger-relevant part is unambiguous (a file described as "minimal, with X section" passes when X is the element that triggers the behavior and the command that consumes it is shown). Nothing needed to trigger the behavior may be left for a stranger to guess; a vague "some config" or "a file like the issue's" fails. | required |
| Behavior matches issue | The report's artifacts (output excerpts, logs, error text, screenshots described) read against the symptom in the issue body | The artifact shows the specific symptom the issue describes (the same error, wrong value, or missing behavior), not an adjacent one, and the report shows what was expected next to what happened. An artifact that shows a different error, a different feature, or only a restatement of the issue text fails. | required |
| Honest outcome | The report's stated outcome set against its own artifacts | The report states what actually happened and claims no more than its artifacts show: no unsupported root-cause claims, no "everyone / always / every machine" generalizations, no results with no run behind them. A result stated in prose counts as backed when the report gives the exact command and the outcome it produced (for example a control run and its numbers). A clearly evidenced "could not reproduce" passes. A confident claim with no artifact fails. | required |
| Claim comment specific | The claim comment, read against the issue | It refers to this issue's concrete behavior in the author's own words and states what the author will do or has done next. A +1, a bare "claiming this", or boilerplate that would fit any issue fails. It must not assert results the report does not back. | required |
| Repo conventions and AI policy | The claim comment and report against the repo-facts "contribution policy" and "bug reports" lines | The comments respect the repo's stated rules: if the policy bans AI-generated contributions or comments outright, nothing is presented as AI-written; if it requires disclosure (tool and extent) for issue comments or reports, the package includes that disclosure; if it requires own-words comments, the text is the author's own account. A policy that states no ask for comments, or no AI policy at all, passes. | required |
| Minimal and scoped | Report body | The reproduction is the smallest case that shows the behavior; unrelated findings are kept out. | preferred |

## Verdict rule

Accept (ready to post) if every required check applicable to the package state passes. Reject (hold) if any applicable required check fails. `unclear` on an applicable required check counts as fail. In live mode on a claim-only draft, checks that need the repro report are reported `unclear` with "not yet applicable: claim-only draft" and are left out of the rule. Preferred checks never change the verdict.
